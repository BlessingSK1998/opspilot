# Decisions

| # | Decision | Alternatives | Rationale |
|---|----------|--------------|-----------|
| 1 | Project lives in `apps/opspilot/` of the existing monorepo | New repo | Matches repo conventions; CI uses `working-directory`. Can be split out with `git subtree`. |
| 2 | Default model `gpt-4o-mini`, overridable via `OPENAI_MODEL` | gpt-4.1-mini, newer | Cheap, supports Structured Outputs; verify name against docs in M3. |
| 3 | Dependencies added per milestone, not up front | Install everything now | Keeps each milestone's lockfile honest and installs fast. |
| 4 | Compose has only postgres + api in M1; dashboard/n8n added in M7/M9 | Stub services | No placeholder services that cannot start. |
| 5 | Mock provider is selected automatically when `OPENAI_API_KEY` is empty | Explicit flag | Zero-config demo for reviewers. |
| 6 | Order lines stored as JSONB on `orders` (no `order_lines` table) | Normalised table | Spec lists a fixed table set; lines are always read with the order and never queried across orders. |
| 7 | Integration tests use embedded Postgres (`pgserver`) unless `TEST_DATABASE_URL` is set | Docker-only (testcontainers) | Real Postgres (enums, JSONB, checkpointer) with zero setup on any laptop or CI runner; compose Postgres still used for `make up`. |
| 8 | Inbound emails are not inserted by `make seed`; they go through `POST /ingest` | Pre-populate messages/tasks | Dashboard data then comes from the real pipeline, so what a reviewer sees is what the system produces. Seed loads reference data only. |
| 9 | Seed data is generated deterministically (fixed RNG seed, reportlab `invariant=1`) and committed | Generate on demand only | Reviewers see the data without running anything; a test proves regeneration is byte-identical. Ground truth is written by the same code as the emails so they cannot drift. |
| 10 | Eval set is deliberately escalation-heavy (~1/3 of emails) | Realistic base rate (~10%) | A realistic base rate would leave too few positives to measure escalation recall. README states production rates would be lower. |
| 11 | Supplier delivery notes/certificates do not require `amount`/`due_date`; supplier invoices do | Require for all | A certificate has no amount. Required-field list is per document type. |
| 12 | `access_or_it_request` with `manager_approval=false` is a *validation issue* (awaiting approval), not an escalation | Escalate | Hard escalation rules in the brief are an explicit list; stay within it. |
| 13 | Low-confidence escalation (<0.7) is not labelled in ground truth | Label vague emails | It is a runtime model signal. Vague emails are flagged `ambiguous` and reported separately in eval. |
| 14 | Order value for the €5,000 rule = SKU unit price x quantity from the product table (net); invoices/refunds use the stated gross amount | Always gross | Orders carry no stated amount, so it must be computed. |
| 15 | Default `OPENAI_MODEL=gpt-4.1-mini` (supports Structured Outputs + temperature 0). Web search could not confirm the single newest cheap model; GPT-5.x reasoning models reject `temperature`, so the provider omits it for `gpt-5*`/`o*` | Newest GPT-5.x mini | Predictable determinism for classify/extract. Override with `OPENAI_MODEL`; pricing table in `llm/pricing.py` is approximate and unverified against the live pricing page. |
| 16 | `LLMProvider` is task-oriented (`classify/extract/assess_risk/draft`), not a raw `complete()` | Generic completion interface | The mock can implement tasks directly; prompts and schemas stay behind the provider. |
| 17 | Mock provider sees only sanitised text, like the real model, and is not an oracle | Mock reads ground truth | Offline eval numbers are honest about what simple rules achieve. |
| 18 | Nodes are `(OpsState, Deps) -> partial state update` functions; `Deps` = provider + backend (reference reader + sink) | Classes with hidden state | Pure and individually testable; the same nodes run against Postgres or in-memory backends. |
| 19 | Read/write ports (`Reference`, `Sink`) with SQL and in-memory implementations | Eval talks to Postgres | Offline eval of 80 emails runs in seconds without a database; the production path uses identical node code. |
| 20 | Agent "tools" are typed functions with Pydantic arg schemas, exported as OpenAI function specs (`tool_specs()`), invoked deterministically by nodes | Free-form LLM tool loop | Predictable, auditable and cheap; schemas allow a tool-calling model to be dropped in later. |
| 21 | PII masking covers IBANs, phones and *personal-provider* e-mails; business e-mails stay | Mask all e-mails | Business addresses/domains are needed to match customers. Reversible via `pii_map`. |
| 22 | SLA clock starts at message `received_at`; "requested date in the past" is judged against `received_at`, not wall clock | Wall clock | Deterministic, and correct for backlogs and for the fixed-date synthetic data. Demo ingestion rebases timestamps to "now". |
| 23 | Any validation issue routes to an info request (awaiting_customer) | Only missing fields | A wrong invoice number or mismatched amount needs customer clarification before anyone acts on it. |
| 24 | Priority = most urgent of (rules, LLM urgency); LLM may raise priority but never lower or suppress an escalation | LLM decides | Keeps escalation recall deterministic and explainable. |
| 25 | Mock rules were written against the same templates as the synthetic emails | Hold out a separate set | Mock-mode eval is therefore a regression test, **not** a generalisation claim. README and eval report say so; real-model numbers are the meaningful ones. |
| 26 | Escalated cases get a draft *before* `human_review` (draft → queue_review → interrupt → create_task) | Interrupt before drafting | The brief's reviewer must approve / edit / reject something concrete. The route order differs slightly from the brief's diagram; the behaviour (human gate before any task is final) is identical. |
| 27 | `queue_review` creates the `pending_review` task *before* the interrupt; `create_task` upserts the same row | Create task only after review | LangGraph re-executes the interrupted node on resume, so side effects must not live in it; and the review queue needs the row while the run is paused. |
| 28 | Review outcomes: approve/edit → `ready_to_send` (or `awaiting_customer` for info requests); reject → `rejected`. `TaskStatus.approved` exists but is unused | Separate approved state | Fewer states for operators; the approval itself is audited in `review_decisions`. |
| 29 | Draft guardrail: identifiers (SKU, order/invoice/PO numbers) and EUR amounts in a draft must appear in the supplied facts, else the draft is replaced by a neutral template and a warning is recorded | Trust the model | "Never invent order details" enforced in code, not only in the prompt. |
| 30 | Run row is created together with the message in `register_message`; duplicates get a completed run pointing at the original message | Create run in API layer | One transaction, and `GET /runs/{id}` works for duplicates too. |
| 31 | API key via `X-API-Key` header, constant-time compare; `/health` is open (for container health checks) | OAuth/JWT | Matches the brief; the key is an env var, never in the repo. |
| 32 | `/ingest` accepts JSON or multipart `.eml` in one route, documented via `openapi_extra` | Two routes | Matches the brief's single endpoint. |
| 33 | `PATCH /tasks/{id}` refuses tasks in `pending_review` (409) and writes an audit event for every manual change | Allow any status change | The human gate cannot be bypassed around the graph; every human action is audited. |
| 34 | Dashboard-support endpoints added: `/samples`, `/simulate/stream` (SSE), `/graph`, `/eval/latest`, `/reviews/pending` | Dashboard reads DB directly | The brief requires the dashboard to talk to the API only. |
| 35 | Dashboard is Streamlit `st.navigation` with one file per page under `dashboard/views/`; one `theme.py` (CSS + Plotly template) and one `api.py` client | Single long script | Clear structure; pages are testable headlessly with Streamlit `AppTest` against a stubbed API. |
| 36 | Source highlighting = exact `source_span` strings wrapped in `<mark>` in the original body | Fuzzy matching | Spans are quoted verbatim by the extractor, so exact matching is both simple and a traceability check. |
| 37 | Run Inspector renders the Mermaid graph via mermaid.js from a CDN inside `components.html` | Pre-rendered PNG | Always in sync with `graph/build.py::MERMAID`. Needs internet for the diagram only; the trace table works offline. |
| 38 | Escalation is scored two ways: *system* (run actually interrupted, includes the low-confidence safety net) and *rules-only* (matches the labelled hard rules) | One number | Recall is what matters; the system number is what operators experience, the rules number shows what the labels measure. Unneeded low-confidence escalations are listed as false positives. |
| 39 | Extraction matching: exact for ids/numbers/lists, tolerance 0.01 for amounts, fuzzy (0.85) only for free-text fields | All fuzzy | Strict where a wrong digit costs money. Free-text `reason` is canonical English in ground truth, so German free text scores as an error: kept visible as an honest finding. |
| 40 | Checkpoint serializer allow-lists OpsPilot's state types (`graph/serde.py`) | Ignore LangGraph's deserialisation warning | LangGraph announced it will block unregistered types; tests also run with `LANGGRAPH_STRICT_MSGPACK=true`. |
| 41 | CI fails if mock-mode accuracy < 0.90 or escalation recall < 0.95 | Report only | Brief requires a threshold gate; thresholds leave headroom while still catching real regressions. |
| 42 | Real-model run (gpt-4.1-mini, 2026-11-20): default model confirmed working with Structured Outputs; cost/message is computed from the price table in `llm/pricing.py`, not from an invoice | Wait for billing data | Gives first real numbers now; the README flags the cost figure as unreconciled. |
| 43 | Use `127.0.0.1` rather than `localhost` for all internal URLs | `localhost` | Python could not resolve `localhost` in the build environment, which made the demo launcher time out and kill the servers. |
| 44 | Docs-vs-report test checks the README against the latest report of *each* provider | Latest file only | Both tables in the README stay tied to real report files. |
| 45 | Personal inbox = a *profile* on each e-mail (`ops` default / `personal`), not a global mode or a second app | Global setting; separate service | One pipeline and one database serve both mailboxes; the profile picks categories, classifier prompt, routing and draft style. Existing behaviour and its eval are unchanged. |
| 46 | Six new categories (job_application_update, job_alert, newsletter_or_promo, finance_notice, account_or_security, personal_message) added to the existing enum via Alembic `0002` | New table or free-text label | Reuses all downstream code; PostgreSQL 16 allows `ADD VALUE` inside the migration transaction. |
| 47 | Informational personal mail (rejection, receipt, statement, account notice) is **closed**, not archived; only junk categories are archived | Archive everything with no reply needed | This was the reported failure: real application replies vanished as "irrelevant". Closed tasks stay visible under their own team. |
| 48 | Personal profile never produces an info-request draft; missing fields are only recorded | Ask the sender | Nobody asks a recruiter or a bank for "missing information". |
| 49 | If the model returns a category outside the mailbox profile, it is replaced by the profile's fallback with confidence <= 0.5 (so a human reviews it) | Trust the model | Defensive: the schema allows all categories, the prompt only some. |
| 50 | Junk categories skip extraction | Extract anyway | Their schemas are empty, which OpenAI strict structured outputs reject (found on the live API); also saves cost. |
| 51 | `/ingest/batch` records a failing e-mail as `failed` and continues | Fail the whole batch | One provider error must not lose 30 other messages. |
| 52 | The personal eval set is synthetic (invented names/companies, written to mirror real patterns); real inbox messages are never committed | Commit anonymised real mail | Privacy; the real inbox is used only as a local smoke test. |
| 53 | Mailbox connection = read-only IMAP poller (`sync/imap_sync.py`) with a Gmail app password in `.env` | Gmail API with OAuth; n8n only | Works with any provider, no OAuth app or consent screen to host, and the code can be tested against a fake server. Read-only select + `BODY.PEEK[]` means it cannot alter the mailbox. Trade-off: app passwords need 2-step verification and are a weaker credential than OAuth. |
| 54 | The sync calls `/ingest` over HTTP and persists only the last UID (plus UIDVALIDITY) in a state file | Write to the DB directly; track UIDs in Postgres | Same code path as any other client (and works against the Docker API); no new table. A failed ingest stops the pass so order is kept and the message is retried. |
| 55 | I (the assistant) do not handle the mailbox password: the user writes it into `.env` themselves | Pass it through chat | Credentials stay out of the transcript and out of tool calls. |
